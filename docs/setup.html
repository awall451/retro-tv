Batocera 43.1 on a Raspberry Pi 4. Last updated 2026-11-05.

Base setup

From a blank microSD card to a Pi that boots Batocera, keeps its data on the SSD, accepts SSH by key, has a fixed address, and runs the case fan.

1. Flash Batocera to the microSD card

  1. Download the image

    From batocera.org, the Raspberry Pi 4 build (bcm2711). Used here: batocera-bcm2711-43.1-20260530.img.gz, 2.2 GB. Check it against the published .md5 file next to it.

  2. Identify the card

    In PowerShell, Get-Disk shows each disk's number, bus and size. The card reader shows as USB, about 29.7 GB for a 32 GB card. Check what is on it first: the card used here still had a 2021 Raspberry Pi OS on it, which was confirmed as a spare before erasing.

  3. Write it with tools/flash-sd.ps1

    Run from an elevated PowerShell (Windows asks for admin). The script refuses any disk that is a boot or system disk, not on USB, or not 28–33 GB; clears the partitions; decompresses the image straight to \\.\PhysicalDriveN; writes the first 1 MB last so Windows doesn't mount half-written partitions; then reads the card back and compares SHA-256.

    powershell -ExecutionPolicy Bypass -File tools\flash-sd.ps1 -Image <path>\batocera-bcm2711-43.1-20260530.img.gz -DiskNumber 1 -Log flash.log

    Expected result: RESULT: VERIFIED, about 6.98 GB written.

Lesson learned

The first run failed at the very end: PowerShell's [math]::Min picked a 32-bit overload and couldn't hold the 6.98 GB size. Everything except the partition table had been written. Sizes in the script are now cast to [int64].

2. Move storage to the SSD

Batocera keeps everything you change (ROMs, saves, settings) in /userdata. Out of the box that's a partition on the card; it belongs on the SSD.

  1. Make the SSD ext4, keeping its data

    The SSD was ext3, which isn't on Batocera's supported list. It was upgraded in place from Raspbian, without reformatting:

    sudo umount /dev/sdX1
sudo tune2fs -O extents,uninit_bg,dir_index /dev/sdX1
sudo e2fsck -fD /dev/sdX1

    Change the drive's type to ext4 in Raspbian's /etc/fstab too. Back up first. This SSD's filesystem is on the whole disk, with no partition table; Batocera handles that fine.

  2. Copy the card's /userdata to the SSD

    Batocera uses a folder named batocera on the external drive as /userdata (read in /etc/init.d/S11share). Copying the card's data there first keeps settings, Bluetooth pairings and the SSH key:

    mkdir /media/sdb/batocera
cp -a /userdata/. /media/sdb/batocera/
  3. Point Batocera at the SSD by UUID

    In /boot/batocera-boot.conf (remount /boot read-write first):

    sharedevice=DEV a9c92283-e75c-4f99-9745-9458be449d7f

    Using the UUID survives the drive's name changing (it was sdb, then sda after a reboot). If the SSD ever fails to mount, Batocera falls back to the card instead of failing to boot. The menu's System settings → Storage device does the same thing.

  4. Verify after a reboot 
    df -h /userdata          # should show /dev/sda, about 916 G
findmnt /userdata        # /dev/sda[/batocera]

3. SSH by key

SSH is on by default (root / linux). A dedicated key lets scripts and tools connect without a password:

ssh-keygen -t ed25519 -N "" -C batocera-pi -f ~/.ssh/batocera_ed25519
ssh root@batocera.local "mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo '<contents of batocera_ed25519.pub>' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Root's home is /userdata/system, so the key lives on the SSD and survives Batocera updates. The private key never goes in this repo (.gitignore blocks it).

Use the IP address

batocera.local relies on mDNS, which was unreliable from Windows. <pi-ip> always works.

4. Fixed address

Batocera gets its address by DHCP. A router reservation pins it: the Pi's wired MAC → <pi-ip>. Don't also set a static IP on the Pi. (The reservation predates Batocera: it was made for the same Pi under Raspbian, and carried over because it follows the network card.)

5. Argon ONE fan and power button

The case's fan and button need Batocera's rpi-argonone service, which talks to the case over I2C. Two changes, then one reboot:

# /boot/config.txt, under [all]
dtparam=i2c_arm=on
dtparam=i2c-1=on
enable_uart=1

# /userdata/system/batocera.conf
system.power.switch=ARGONONE

Batocera's own setup script adds the config.txt lines on first start, but they only take effect at the next boot; adding them by hand saves a reboot. Check after booting:

i2cdetect -y 1                  # 1a should appear
ps -eo args | grep [r]pi-argonone

Default curve: off below 55 °C, 10% at 55, 55% at 60, 100% at 65. Change it in /userdata/system/configs/argonone.conf (lines like 50=30). A short press on the case button shuts down cleanly, a double press quits the current game.

This unit's fan doesn't spin

The board answers at 0x1a and accepts i2cset -y 1 0x1a 0x80 100 (the service's own command), and a 0=100 curve held it at full speed, but the fan stayed silent. That points to the fan's 2-pin cable or the fan itself. Temperatures stayed at 49–56 °C with no throttling (vcgencmd get_throttled = 0x0) on the case alone.

6. BIOS files

BIOS files came from the Miyoo backup. tools/check_bios.py compares each file's MD5 with Batocera's list in /usr/share/batocera/datainit/bios/readme.txt:

FileSystemResult
scph5501.binPlayStation (US)Good
gba_bios.bin, gb_bios.bin, gbc_bios.binGBA, GB, GBCGood
bios_CD_U/E/J.binSega CDGood
syscard3.pcePC Engine CDGood after stripping a 512-byte header: tail -c +513
neogeo.zipNeo GeoDifferent zip full FBNeo set, should work

The PS1 emulator log confirms the BIOS loads: found BIOS file: scph5501.bin. The menu still warned before every PS1 game, because it wants all seven PS1 BIOS versions. The pre-launch check is off (CheckBiosesAtLaunch=false in es_settings.cfg), so run check_bios.py when adding a new system.

7. Airplane mode recovery

The Control Center's Plane Mode stops Bluetooth and Wi-Fi, which disconnects the controller you'd use to switch it back. Wired SSH still works:

batocera-planemode disable
/etc/init.d/S32bluetooth restart
bluetoothctl show | grep Powered      # Powered: yes

Pairings survive; press the controller's PS button. The toggle is now removed from the Control Center (see HDMI and Trinitron).
